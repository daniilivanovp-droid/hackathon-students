# Правила работы агентов над моделью Capibara

## Источники истины

1. `docs/handout.md` — условия кейса и состав исходных данных.
2. `docs/tasks.md` — действующие вопросы аналитиков; файл может пополниться в ходе хакатона.
3. `docs/architecture.md` — согласованная целевая архитектура и определения показателей.
4. `docs/implementation-task.md` — порядок работ, критерии готовности и отметки о выполнении.

Если документы расходятся, сначала сверяйтесь с условиями кейса. Не меняйте бизнес-определения по догадке.

## Согласование решений

Пользователь просит согласовывать каждое важное решение. Уже зафиксированные в `docs/architecture.md` решения повторно согласовывать не нужно. До изменения уровня детализации таблиц, ключей, определения выручки или покупателя, политики обработки отсутствующих данных, структуры слоёв либо стратегии сборки предложите пользователю конкретные варианты с последствиями и дождитесь ответа. Пока ответ ожидается, выполняйте независимые задачи. Локальные правки, необходимые для исполнения согласованного решения, делайте самостоятельно.

## Границы данных и кода

- `raw` и CSV в `data/` сохраняйте без преобразований; изменения типов и нормализацию делайте в `core`.
- Ответы аналитикам считайте из `core` или `mart`, не напрямую из `raw`.
- Не соединяйте позиции, платежи и отзывы друг с другом на уровне заказа без предварительной агрегации: так умножаются строки и суммы.
- Сохраняйте все исходные строки либо останавливайте сборку с явной ошибкой. Не скрывайте потери строк с помощью `DISTINCT`, произвольной дедупликации или внутреннего `JOIN`.
- Для денежных значений используйте `numeric`, для дат — типизированные временные поля, для почтового индекса — текст, сохраняющий ведущие нули.
- Каждый SQL-скрипт должен запускаться повторно; сборка модели и проверки должны проходить в одной транзакции.
- Тексты документации и новых комментариев пишите по-русски. Имена SQL-объектов и обязательные английские подписи категорий оставляйте согласно архитектуре.

## Работа с задачами

Перед началом выберите пункт в `docs/implementation-task.md` и проверьте его зависимости. Отмечайте `[x]` только после выполнения указанного критерия и запишите рядом краткое доказательство: команду, результат или путь к артефакту. Если проверка недоступна, оставьте `[ ]` и укажите причину. При параллельной работе не редактируйте одновременно один файл без координации.

По каждой порученной задаче напишите короткий отчёт простыми словами в своём файле `docs/agent-reports/`: **что сделали**, **как проверили**, **что осталось или мешает**. Не смешивайте отчёты разных агентов и не называйте неподтверждённый результат проверенным. Тимлид переносит подтверждённые итоги в общий чек-лист.

После изменений проверяйте соответствующий сценарий из `docs/implementation-task.md`. Для SQL-сборки обязательны запуск на чистой базе, повторный запуск и проверка отката при ошибке. Если Docker недоступен, выполните доступные статические проверки и явно зафиксируйте, что интеграционная проверка не проводилась.

## Результат для сдачи

Нужны воспроизводимая сборка `core` и `mart`, SQL-ответы и числа, проверки качества, короткая записка о решениях (не более половины страницы), концепция дашборда и стратегия развития. Новые пять вопросов из `docs/tasks.md` добавляйте в план и покрывайте из модели после их публикации.
