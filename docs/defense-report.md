# Отчёт о выполнении и подготовка к защите

## 1. Что было сделано

Для маркетплейса Capibara построена воспроизводимая модель на PostgreSQL 16 поверх восьми исходных CSV. Слой `raw` хранит выгрузки без изменения структуры и типов, `core` содержит восемь типизированных таблиц, `mart` — пять витрин для расчётов. SQL сборки — [01_build_core.sql](../model/01_build_core.sql), проверки — [03_quality_checks.sql](../model/03_quality_checks.sql), ответы — [02_answers.sql](../model/02_answers.sql), единый запуск — [run.sh](../model/run.sh).

В [implementation-task.md](implementation-task.md) выполнены все опубликованные пункты, кроме `N-01`: ещё пять вопросов должны появиться в `docs/tasks.md` позже. Работа каждого агента и оставшиеся оговорки описаны простыми словами в [отчётах агентов](agent-reports/). Исходные требования находятся в [handout.md](handout.md) и [tasks.md](tasks.md); полный набор архитектурных правил — в [architecture.md](architecture.md).

## 2. Как устроен поток данных

1. `bash scripts/setup.sh --reset` поднимает контейнер PostgreSQL, создаёт схемы и загружает CSV в `raw`. При чистой установке загружено **550 759 строк**: 99 441 заказ, 112 650 позиций, 103 886 платежей, 99 224 отзыва, 32 951 товар, 3 095 продавцов, 99 441 запись покупателя и 71 перевод категории. [Протокол установки](e04-success.md).
2. `bash model/run.sh` переносит данные в `core`, создаёт витрины и выполняет проверки качества **в одной транзакции**. Если проверка падает, предыдущая рабочая модель остаётся доступной. После успешной фиксации скрипт печатает ответы. Оба shell-скрипта проверены в Git Bash без ручного изменения `PATH`: они находят установленный Docker Desktop в стандартной папке.
3. Повторная сборка прошла на тех же исходных данных. Чтобы проверки ключей не тратили несколько минут на временные файлы, скрипт задаёт `work_mem = 64MB` только для транзакции сборки. Это не меняет данные и постоянные настройки сервера. [Отчёт о повторе и откате](agent-reports/quality-run.md).

Прямой запрос к `raw` не считается ответом аналитикам: он обошёл бы договорённости о типах, связях и показателях. Все пять ответов читают `core`/`mart`.

**Состояние рабочей машины.** Docker Desktop оказался уже установлен и запущен; его CLI не был в обычном `PATH`, поэтому оба shell-скрипта научены находить стандартную папку установки. С разрешения пользователя через `winget` дополнительно установлен Python 3.12. При проверенном запуске `py -3` выбрал также имевшийся в системе Python 3.14, а `setup.sh` установил для него `psycopg2-binary`. Системный `PATH` постоянно не менялся. Локальный контейнер PostgreSQL проекта остаётся запущенным после проверки.

## 3. Зерно и ключи — что объяснять на защите

| Сущность | Одна строка | Ключ и причина |
| --- | --- | --- |
| `core.orders` | заказ | `order_id`; статус и даты принадлежат всему заказу. |
| `core.order_items` | одна единица товара одного продавца в заказе | `(order_id, order_item_id)`; `order_item_id` — лишь номер внутри заказа. |
| `core.order_payments` | запись оплаты | `(order_id, payment_sequential)`; один заказ может иметь несколько платежей. |
| `core.order_reviews` | отзыв о заказе | `(review_id, order_id)`; один `review_id` в исходном файле повторяется, а составная пара не повторяется. |
| `core.customers` | запись покупателя при заказе | `customer_id`; для подсчёта людей используется другой, стабильный `customer_unique_id`. |
| `core.products`, `core.sellers` | карточка товара и продавец | `product_id`, `seller_id`; позиция ссылается на оба справочника. |
| `core.categories` | португальская категория или отсутствие категории | Технический `category_id`; исходное имя и английская подпись хранятся отдельно. |

В CSV `review_id` повторяется в **814 строках**, у **547 заказов** больше одного отзыва, но пара `(review_id, order_id)` уникальна. Поэтому использовать один `review_id` как PK или соединять отзыв с позициями без агрегации было бы ошибкой. У одного заказа также может быть несколько позиций и несколько платежей: прямое соединение этих двух фактов умножит суммы. Витрина `mart.order_financials` сначала суммирует позиции до уровня заказа, затем соединяет заказ и покупателя.

Индекс почты хранится как `text`: это часть адреса, а не измеряемое число; так будущие значения с ведущим нулём сохранятся буквально. Денежные поля имеют тип `numeric`, даты — `timestamp`. Часовой пояс источником не указан, поэтому модель его не выдумывает.

## 4. Почему показатели считаются именно так

**Выручка** — сумма `price` по позициям только тех заказов, чей статус `delivered`. `freight_value` и платежи в неё не входят. Так мы не объявляем выручкой недоставленный заказ и не размножаем деньги из-за нескольких платежей. Для продавца суммируются только его собственные позиции, даже если в заказе были другие продавцы.

**Средний чек** — среднее полной стоимости доставленного заказа: сначала `sum(price + freight_value)` по его позициям, затем `avg` по заказам. Доставка включена, потому что чек описывает всю оплату заказа. Среднее по строкам позиций дало бы другой ответ. Одна строка `order_items` соответствует одной единице товара, поэтому среднее число строк и единиц в этом снимке совпало: **1.14**.

**Покупатель и повторная покупка** — `customer_unique_id` с одним или хотя бы двумя **оформленными заказами любого статуса**. Это решение отдельно согласовано с пользователем после проверки противоречия: по всем заказам получается контроль **96 096 / 2 997 / 3,12%**, а по одним доставленным — **93 358 / 2 801 / 3,00%**. Денежная выручка в `mart.customer_orders` по-прежнему относится только к доставленным заказам.

**Категория** — каждая карточка товара обязательно получает категорию. В исходном файле у 610 товаров она пуста: для них создана явная запись `Non category`. Две португальские категории есть у товаров, но отсутствуют в справочнике переводов: `pc_gamer → gaming_pcs` и `portateis_cozinha_e_preparadores_de_alimentos → portable_kitchen_and_food_processors`. Остальные 71 перевод взяты из источника. Португальский ключ и происхождение перевода сохраняются, поэтому категории не сливаются молча. Сумма выручки 74 категорий равна общей выручке.

**Месяц продажи** — месяц оформления заказа. Общая витрина `mart.monthly_sales` содержит все месяцы, встречающиеся в данных: сейчас их **25** с сентября 2016 по октябрь 2018. Первый запрос отдельно строит календарный ряд из **24** месяцев с сентября 2016 по август 2018 и присоединяет витрину через `LEFT JOIN`. Поэтому ноябрь 2016, когда нет продаж, остаётся строкой с нулём. Новые периоды не требуют переписывать витрину.

## 6. Как доказали, что ничего не потерялось

- Проверены количества всех восьми источников и равенство строк в семи одноимённых таблицах `raw`/`core`. Справочник категорий проверяется отдельно: 71 перевод источника + 2 ручных + 1 `Non category`.
- До пересборки модель проверяет повторные ключи и потерянные связи в `raw`. В `core` работают PK, FK и обязательные поля. Неверные типы вызывают ошибку приведения, а не тихую потерю строки.
- На живой базе временно добавили дубль заказа и позицию без заказа. Предварительная проверка назвала конкретную ошибку. Обе тестовые вставки были откатаны. [Отчёт по модели](agent-reports/core-model.md).
- Отдельно временно присвоили товару неверную категорию. Проверка обнаружила несоответствие исходнику, транзакция откатилась и исходная категория восстановилась. [Отчёт по качеству](agent-reports/quality-run.md).
- Сумма доставленных цен сверена пятью путями: через позиции, заказы, месяцы, продавцов и категории. Все дали **13 221 498.11**.
- Повторный запуск модели прошёл. Затем в SQL-поток добавили намеренную ошибку **после** сборки и проверок. `psql` завершился с ошибкой, а идентификаторы старых объектов, число заказов и сумма выручки до и после совпали. Ошибка не записывалась в файлы проекта.

## 7. Вопросы, которые вероятны на защите

**Почему нельзя взять общую сумму заказа для каждого продавца?** В одном заказе бывают товары нескольких продавцов. Общая сумма размножилась бы; продавцу принадлежит только `price` его позиций.

**Почему платежи не равны выручке?** Платёжный сервис записывает несколько способов и частей оплаты одного заказа. Оплата и доставленная продажа описывают разные события; выручка задана через доставленные товарные позиции.

**Почему средний чек 159.88, а не 123.75 или 139.97?** Эти два числа получаются на уровне строки товара. Наш расчёт сначала собирает полный чек заказа с доставкой, затем усредняет заказы.

**Почему повторных считают по всем заказам, если выручка только по доставленным?** Это разные показатели. Вопрос о покупателе и повторе описывает факт оформления; контроль задания подтверждает такой выбор. Выручка описывает доставленные товары.

**Почему не хватает одного `customer_id`?** Он привязан к записи покупателя в конкретном заказе. Для одного человека встречается несколько таких записей; `customer_unique_id` сохраняется между покупками.

**Почему категория `Non category` отдельная?** Без неё `JOIN` выбросил бы товары с пустой категорией, и сумма категорий была бы меньше общей выручки. Явный ключ делает пропуск видимым.

**Почему ручной перевод не перезаписывает исходник?** Португальское имя остаётся исходным ключом, английское — подписью, `translation_source` показывает, откуда она взята. Если источник позже пришлёт перевод этих двух категорий, модель отдаст ему приоритет после обновления контрольного числа строк нового снимка.

**Почему месячный отчёт имеет 24 строки, а витрина — 25 месяцев?** Отчёт отвечает на строго заданный период и добавляет отсутствующий ноябрь 2016. Витрина общая и уже содержит сентябрь–октябрь 2018 для новых вопросов.

**Как ведёт себя модель при испорченном источнике?** Сборка останавливается с названием проблемы: дубль ключа, сиротская связь, неверный тип или несходящаяся сумма. Транзакция не публикует частично новую модель.

**Почему полная пересборка, а не инкрементальная?** Для текущих 550 759 строк простая полная сборка воспроизводима и легко проверяется. Когда появятся частые большие обновления, понадобятся правила поздних изменений и инкрементальная обработка.

**Почему не звёздная схема?** Сейчас восемь типизированных сущностей сохраняют исходные связи и зерно без дополнительного дублирования. Отчётные уровни явно задают витрины; новую схему имеет смысл вводить по измеренной нагрузке и новым вопросам.

**Что первым станет узким местом?** Время полной пересборки и тяжёлых группировок. Для текущего запуска ускорение `work_mem` уменьшило время повторной сборки; дальше нужны индексы, измерение планов и партиционирование. Переход к колоночному хранилищу рассматривается только при измеренном превышении окна обновления или времени ответа. Подробности — в [стратегии развития](growth.md).

**Какие показатели дашборда нельзя складывать?** Средний чек и доли нужно пересчитывать из числителя и знаменателя. Один заказ может попасть к двум продавцам или категориям, поэтому их количества заказов нельзя складывать в общий итог. Уникальных покупателей по месяцам также нельзя суммировать. [Концепция дашборда](dashboard.md).
